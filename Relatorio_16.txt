4. PRICE_RULES (docs 07 §2, 10 §§2-3):
- Só ADMINISTRADOR cria/altera (require_roles); CLIENTE/PRESTADOR => 403.
- perfil_alvo distingue regra comercial do CLIENTE vs PRESTADOR.
- Faixa de quantidade + valor unitário + vigência; valores negativos =>
  422 (Pydantic ge=0; CHECK do banco preservado); faixas inválidas => 422.
- Sobreposição de faixas ATIVAS do mesmo perfil com vigências que se
  cruzam => 409 (ambiguidade de cálculo impossível). Regras desativadas
  não bloqueiam novas faixas. Sem DELETE: desativação por ativo=false
  preserva histórico utilizado por coletas antigas.
- Toda criação/alteração grava AuditLog (user admin, entidade price_rules,
  valor_anterior_json/valor_novo_json incluindo justificativa, ip_origem,
  UTC).

5. FECHAMENTO FINANCEIRO (docs 03 §4, 06 §5.1.2, 07 §3):
- Estado exigido: CARREGADA; posse via _coleta_do_provider com FOR UPDATE.
- Quantidade = COUNT(tires) (registros individuais), nunca a declarada.
- Regra aplicável por lado: ativa, faixa contém a quantidade, vigência na
  data de hoje. Faltante => 409 nomeando CLIENTE ou PRESTADOR, sem
  persistir nada.
- Cálculo Decimal com ROUND_HALF_UP, 2 casas; cliente e prestador
  calculados separadamente (independência comercial).
- Snapshot imutável em collections.snapshot_valor_cliente/prestador +
  data_finalizacao; dois FinancialTransaction independentes (tipo_entidade
  CLIENTE/PRESTADOR, perfil_id = profiles.id de cada parte, PENDENTE);
  transição para FINALIZADA; tudo num único commit (atômico).
- Corpo da requisição: modelo vazio extra=forbid — nenhum valor/ID
  financeiro é aceito do Flutter.

6. IMUTABILIDADE PÓS-FECHAMENTO:
- Re-finalizar => 409 (estado FINALIZADA); mudar estado depois => 409
  (mapa TRANSICOES_VALIDAS não sai de FINALIZADA nesta missão); alterar
  price_rules depois não muda snapshots/lançamentos (provado em teste).

  (setUp/tearDown), mantendo o padrão das demais suítes intocado.

9. DECISÕES TOMADAS:
- Único caminho para FINALIZADA é /finalizar: a rota genérica /status já
  restringe os literais do payload (Literal sem FINALIZADA), então nenhum
  conflito com TRANSICOES_VALIDAS — documentado no STATUS §7.
- Auditoria de preço guarda a justificativa dentro de valor_novo_json
  (AuditLog não possui coluna própria para isso; doc 10 §3.1 atendido).
- PATCH aceita limpar vigencia_fim (None explícito via model_fields_set).
- Sobreposição considera apenas regras ativas; histórico desativado nunca
  bloqueia.
- data_vencimento dos lançamentos = data do fechamento (política de prazo
  é pendência registrada; cobrança/Pix fora do escopo).

10. CONFLITOS DOCUMENTAIS: nenhum silencioso. Doc 07 §3 diz "no exato
instante em que transita para FINALIZADA" — implementado literalmente
(cálculo+snapshot+lancamentos+transição na mesma operação).
