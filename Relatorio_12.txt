3. ENDPOINTS CRIADOS (prefixo /api/v1/profile):
- POST   /client   (201) — cria perfil CLIENTE + linha clients vinculada.
- GET    /client   (200) — retorna o próprio perfil.
- PUT    /client   (200) — atualização parcial (exclude_none).
- POST   /provider (201) — cria perfil PRESTADOR + linha providers (com veículo).
- GET    /provider (200) — retorna o próprio perfil (inclui veiculo).
- PUT    /provider (200) — atualização parcial (campos base, pix e veículo).
Erros: 401 sem token; 403 papel errado; 404 perfil inexistente; 409 duplicado;
422 validação/campos extras.

4. TABELAS UTILIZADAS (nenhuma migration nova — estrutura existente):

- clients (linha 1:1 criada junto do perfil CLIENTE)
- providers (linha 1:1 criada junto do perfil PRESTADOR; dados_veiculo_json)

5. VALIDAÇÕES IMPLEMENTADAS NO BACKEND:
- Schemas com ConfigDict(extra="forbid") — campo desconhecido ou "user_id" no
  corpo => 422 (impossível forjar ownership pelo payload).
- cpf_cnpj normalizado para dígitos; aceito apenas 11 ou 14 dígitos.
- telefone obrigatório, 8–20 caracteres; nome_razao_social 3–200.
- chave_pix opcional (<=140); dados_veiculo_json objeto JSON livre (placa/tipo).
- reputacao_score, taxa_resposta e status_operacional NÃO são aceitos no
  payload — continuam default do banco (5.00 / 100.00 / DISPONIVEL).

6. MECANISMO DE OWNERSHIP:
- O usuário é sempre obtido do token (get_current_user via require_roles);
  o perfil localizado é SEMPRE profiles.user_id == usuario.id do token.
- Nenhum id chega por URL, query ou corpo. Query ?user_id= é ignorada
  (testada: resposta contém os próprios dados do chamador).

7. RBAC:
- Rotas /client exigem role CLIENTE; rotas /provider exigem PRESTADOR
  (require_roles da Missão 06). Papel cruzado => 403 sem header
  WWW-Authenticate (semântica mantida).

11. PROBLEMAS ENCONTRADOS E CORREÇÕES:
- BUG REAL corrigido em criar/atualizar prestador: dados_veiculo_json pertence
  à tabela providers (e não a profiles). Payload agora é dividido: campos base
  + pix em profiles; veículo na linha providers. GET/PUT retornam o veículo
  lendo da tabela correta.
- BUG REAL corrigido nos dois POSTs: db.flush() estava fora do try — violação
  de UNIQUE (cpf_cnpj/user_id) estourava 500 em vez de 409. Unidade de trabalho
  inteira agora protegida por except IntegrityError => rollback + 409.
- Suíte reescrita para ser auto-suficiente (cada teste registra seus usuários e
  gera cpf_cnpj sequencial único): unittest executa métodos em ordem
  alfabética e os dados compartilhados causavam colisões de UNIQUE mascaradas.
