2. COMPORTAMENTO EXISTENTE — CANCELAMENTO ATUAL
=====================================================================

### Endpoint Atual
- **Rota:** `POST /api/v1/collections/{coleta_id}/cancelar`
- **Método HTTP:** POST
- **Auth:** `Authorization: Bearer <JWT>`
- **Role permitida:** `CLIENTE` (via `require_roles("CLIENTE")`)
- **Body:** `{}` (vazio estrito — Pydantic `extra="forbid"`)
- **Idempotência:** NÃO implementada (não aceita `X-Idempotency-Key`)
- **Outbox:** NÃO utilizado (decisão arquitetural — Missão 37)

### Validações no Backend (collections.py:411-429)
1. Usuário autenticado com role CLIENTE
2. Perfil Cliente existe (`_client_do_usuario`)
3. Coleta existe e pertence ao cliente (`coleta.client_id == client.id`)
4. **Estado obrigatório:** `coleta.status == "SOLICITADA"`
5. Se estado ≠ SOLICITADA → HTTP 409: `Transição inválida a partir de {status}.`

### Respostas
- **200 OK:** `{"id": "<uuid>", "status": "CANCELADA"}`
- **401:** Token inválido/ausente
- **403:** Role ≠ CLIENTE
- **404:** Coleta não encontrada ou não pertence ao cliente (anti-enumeração)
- **409:** Estado atual ≠ SOLICITADA

### Máquina de Estados Atual (TRANSICOES_VALIDAS)
```python
TRANSICOES_VALIDAS = {
    "RASCUNHO": {"SOLICITADA"},
    "SOLICITADA": {"ACEITA", "CANCELADA"},

    "EM_DESLOCAMENTO": {"EM_CONFERENCIA"},
```

**Observação crítica:** O estado `ACEITA` tem `CANCELADA` em `TRANSICOES_VALIDAS`, mas o endpoint `/cancelar` atual **bloqueia** explicitamente qualquer estado ≠ SOLICITADA (linha 425-426).

9. IDEMPOTÊNCIA / OFFLINE
=====================================================================

### Cancelamento Atual (SOLICITADA → CANCELADA)
- **Idempotência:** NÃO implementada
- **Outbox:** NÃO utilizado
- **Motivo (Missão 37):** Endpoint não possui idempotência no backend
- **Risco:** Duplo clique bloqueado no Flutter; se rede cair após sucesso, reenvio criaria erro 409 (já cancelado)

### ACEITA → CANCELADA — Deveria ter Idempotência?
**ANÁLISE:**
- Cancelamento é operação **idempotente por natureza** (cancelar duas vezes = mesmo resultado)
- Mas **sem chave de idempotência**, backend não distingue "reenvio legítimo" de "dupla submissão"
- Se Prestador cancela offline (ex: no local, sem sinal), **precisa de Outbox + Idempotência**
- Se Admin cancela via painel web (sempre online), idempotência menos crítica mas recomendada

### Decisão Pendente
- **IDEMPOTÊNCIA NÃO DEFINIDA** para cancelamento pós-aceite
- Se implementar: novo endpoint ou estender `/cancelar` com `X-Idempotency-Key` + suporte a Prestador/Admin
- Se usar Outbox: adicionar método `agendarCancelamentoColeta` no `OutboxService`
