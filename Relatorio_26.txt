(Relatorio_26.txt)

1. RESUMO DO ESTADO ATUAL

Sistema de coleta e gerenciamento de pneus com aplicativo multiplataforma
(Flutter) e backend assíncrono (FastAPI), cobrindo declaração de carga,
conferência presencial, validação de DOT, financeiro desacoplado e
administração com auditoria.

Arquitetura:
  Flutter/Dart (App Único Multiplataforma: Android, iOS, Web)
      ↓ (REST API JSON sobre HTTPS)
  FastAPI / Python 3.11+ (Pydantic v2 + SQLAlchemy)
      ↓
  PostgreSQL 15+ (Banco Relacional Transacional)

6. DECISÕES CRÍTICAS ATIVAS

- Identidade única do pneu é o UUID interno; número de fogo é identificação física operacional.
- DOT (semana/ano) nunca é identificador único; idade calculada no backend.
- Duplicidade de número de fogo na MESMA coleta: BLOQUEIO definitivo.
- Financeiro com snapshots imutáveis por coleta encerrada.
- Único caminho para FINALIZADA é POST /collections/{id}/finalizar.
- Sobreposição de faixas ativas do mesmo perfil_alvo é bloqueada na criação/alteração.
- API administrativa é SOMENTE LEITURA para coletas/auditoria.
- Idempotência: POST /collections aceita X-Idempotency-Key (UUIDv4).
- Outbox: pneus, conclusão e finalização também aceitam X-Idempotency-Key.
- Contestação: POST /collections/{id}/contestar executa apenas FINALIZADA→CONTESTADA.
- Hardening: rate limiting por IP, cabeçalhos HTTP, limites de entrada.
- Fundação Outbox Offline: fila local PERSISTENTE com retry seguro.
- Disparo automático: início do app, retorno ao primeiro plano e reconexão.
- Sessão: JWT persistido em armazenamento seguro (FlutterSecureStorage).

9. REGRAS INQUEBRÁVEIS

1. Flutter/Dart é o frontend.
2. FastAPI/Python é o backend.
3. PostgreSQL é o banco.
4. Backend é autoridade das regras (revalida tudo no servidor).
5. Cliente, Prestador e Administrador possuem papéis separados.
6. Cada pneu possui registro individual com UUID próprio.
7. DOT NÃO é identificador único.
8. Idade do DOT é calculada pelo backend.
9. Valor do cliente e valor do prestador são independentes.
10. Preços são configurados pelo Administrador.
11. Coletas encerradas preservam snapshots financeiros imutáveis.
12. Código deve ser enxuto e sem abstrações desnecessárias.

10. CONCLUSÃO

O projeto encontra-se em estado estável com 18 missões concluídas
mais a Missão 19 (Sessão e Autenticação no Flutter). O backend
