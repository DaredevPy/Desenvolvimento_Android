3. REGRAS IMPLEMENTADAS (docs 03 §§2.1/18, 04 §2, 05 §1, 10 §§2-3):
- Quem contesta: Cliente dono da coleta ou Administrador (matriz doc 04,
  linha "Confirmar / Contestar coleta realizada": CLIENTE sim, PRESTADOR
  nao, ADMINISTRADOR sim). Prestador recebe 403.
- Única transição aceita: FINALIZADA -> CONTESTADA. Qualquer outro estado
  retorna 409 "Transição inválida a partir do estado atual."; CONTESTADA
  é terminal (segunda contestação => 409 sem novo registro de auditoria).
- Ownership: cliente só acessa a própria coleta; coleta inexistente ou de
  terceiro devolvem o MESMO 404 uniforme "Recurso não encontrado."
  (anti-enumeração). Administrador atravessa ownership por permissão
  explícita dos docs 04/10, inclusive para coleta inexistente (404 igual).
- Payload: corpo vazio estrito (extra="forbid"); campo extra => 422. Os
  docs não definem justificativa/evidências para contestação — registrado
  como pendência em vez de inventar contrato.
- Auditoria: AuditLog(acao="CONTESTACAO_COLETA", entidade_afetada=
  "collections", entidade_id=coleta_id, valor_anterior_json={"status":
  "FINALIZADA"}, valor_novo_json={"status": "CONTESTADA"}, user_id do JWT,
  ip_origem do request) gravado NA MESMA transação da mudança de estado.
- Sem efeitos colaterais: nenhum lançamento novo, nenhum recálculo,
  snapshots intactos, pneus/DOT/NF/itens declarados intactos, nenhum
  evento de reputação automático (fórmula doc 03 §6 segue pendente).

4. PROTEÇÃO CONTRA CONCORRÊNCIA:
- db.get(Collection, id, with_for_update=True) serializa disputas pela
  mesma coleta; UPDATE ... WHERE status='FINALIZADA' decide por rowcount:
  1 => venceu (estado + auditoria commitam juntos); 0 => rollback + 409.
- Teste de corrida (threads + barreira): exatamente um 200 e um único
  registro de auditoria; perdedor recebe 409. sqlite ignora FOR UPDATE,
  mas o UPDATE condicional preserva o resultado único; no PostgreSQL o
  row lock torna o desfecho determinístico.

8. DECISÕES TÉCNICAS:
- Endpoint dedicado /contestar em vez de estender /status: doc 05 §1
  trata contestação como ação específica do Cliente; payload restrito e
  regra própria de ownership (admin atravessa) não cabem na rota genérica,
  cujo enum de novo_status já impede alcançar CONTESTADA.
- Sem nova tabela/migration: status + audit_logs cobrem o requisito
  (código enxuto). Se a mediação ganhar fluxo próprio (parecer,
  evidências), avaliar modelo dedicado naquela missão.
- /contestar NÃO aceita X-Idempotency-Key: operação fora do escopo offline
  do doc 09 §2 (que cobre operações do prestador); pendência registrada
  caso o escopo mude.
- Reputação automática deliberadamente NÃO implementada: fórmula/limiares
  são DECISÃO PENDENTE documental (doc 03 §6); gravar evento agora seria
  inventar regra de negócio.
