## 1. RESUMO EXECUTIVO

Implementada garantia de integridade **no PostgreSQL** para impedir duplicidade de Número de Fogo dentro da mesma coleta, usando um **índice único parcial** que:
- Bloqueia: mesma `collection_id` + mesmo `numero_fogo` (não nulo)
- Permite: coletas diferentes + mesmo `numero_fogo`
- Permite: múltiplos `NULL` na mesma coleta (pneus ilegíveis)

## 2. ARQUIVOS ALTERADOS

### 2.1 Migration Up
**Arquivo:** `backend/db/migrations/004_tire_numero_fogo_unique.sql`
```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_tires_collection_numero_fogo
```

## 4. COMPORTAMENTO PARA NULL

**Múltiplos NULL permitidos na mesma coleta** — confirmado pelo teste `test_19`.

O índice parcial `WHERE numero_fogo IS NOT NULL` exclui valores NULL da verificação de unicidade, permitindo múltiplos pneus "ilegíveis" (`numero_fogo_ilegivel=True`, `numero_fogo=NULL`) na mesma coleta.

---

## 5. COMPORTAMENTO ENTRE COLETAS DIFERENTES

**Mesmo Número de Fogo em coletas diferentes = PERMITIDO** — confirmado pelos testes:
- `test_09` (existente): via API
- `test_21` (novo): inserção direta no banco bypassando validação Python

O índice é composto por `(collection_id, numero_fogo)`, então a unicidade é **por coleta**, não global.

## 11. OBSERVAÇÕES IMPORTANTES

### Validação Python Mantida
A validação em `backend/app/collections.py:_registrar_pneus` (linhas 517-527) continua ativa como primeira camada, retornando erro HTTP 409 amigável antes de chegar ao banco.

### Segunda Camada: PostgreSQL
O índice único parcial atua como **segunda camada de proteção** contra race conditions em requests concorrentes que bypassassem a validação Python.

### Não Alterado
- Regra de DOT (continua sem UNIQUE, repetição livre)
- Ciclo de vida do pneu
- Número de Fogo entre coletas
- `numero_serie` (não validado por enquanto)
- Outbox, Flutter, autenticação, financeiro

### Concorrência
O teste `test_20` confirma que o PostgreSQL bloqueia a duplicidade mesmo com inserção direta (bypass Python). Um teste de concorrência real com threads simultâneas não foi implementado pois o ambiente de testes (SQLite em memória) não suporta adequadamente locks de linha PostgreSQL (`FOR UPDATE`). A constraint de banco garante a integridade em produção.
