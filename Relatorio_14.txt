3. ENDPOINTS CRIADOS (prefixo /api/v1/collections):
- POST  ""                        (201) — cria solicitação (CLIENTE). Status inicial SOLICITADA.
- GET   ""                        (200) — lista as próprias coletas (CLIENTE: como cliente;
                                          PRESTADOR: como prestador atribuído).
- GET   "/disponiveis"            (200) — coletas SOLICITADA sem prestador (PRESTADOR).
- GET   "/{coleta_id}"            (200) — detalhe da própria coleta (CLIENTE dono).
- POST  "/{coleta_id}/aceitar"    (200) — aceite (PRESTADOR), transição atômica
                                          SOLICITADA -> ACEITA; perdedor da corrida recebe 409.
- POST  "/{coleta_id}/cancelar"   (200) — cancelamento pelo dono, somente a partir de
                                          SOLICITADA (doc 05); alheio/inexistente => 404 uniforme.
- POST  "/{coleta_id}/status"     (200) — avanço do prestador atribuído dentro do conjunto
                                          EM_DESLOCAMENTO / EM_CONFERENCIA / CARREGADA,
                                          validado contra o mapa de adjacência.
Erros: 401 sem token; 403 papel errado; 404 inexistente/alheio (corpo idêntico,
anti-enumeração) e perfil ausente; 409 estado/posse inválidos; 422 validação.

4. IDENTIDADE E OWNERSHIP:
- client_id e provider_id NUNCA vêm do corpo/URL/query: obtidos por join
  profiles.user_id == usuario.id do token (fundação Missões 05/06/07).
- Schemas com ConfigDict(extra="forbid"): client_id, provider_id, status,
  snapshot_valor_*, idempotency_key no corpo => 422.
- Detalhe/cancelamento: coleta inexistente e coleta alheia retornam o MESMO 404
  (mesma constante), sem dados do recurso na resposta.
- Avanço de status: coleta não atribuída ao prestador do token => mesmo 404 de
  inexistente; status final confirmado por UPDATE condicional no banco.

5. MÁQUINA DE ESTADOS:
- TRANSICOES_VALIDAS registra o grafo completo do doc 05 (RASCUNHO->SOLICITADA;
  SOLICITADA->ACEITA/CANCELADA; ACEITA->EM_DESLOCAMENTO/CANCELADA;
  EM_DESLOCAMENTO->EM_CONFERENCIA; EM_CONFERENCIA->CARREGADA;
  CARREGADA->FINALIZADA; FINALIZADA->CONTESTADA).
- Exposto nesta missão: ACEITAR, CANCELAR (dono, só SOLICITADA) e avanço do
  prestador até CARREGADA. FINALIZADA/CONTESTADA/RASCUNHO permanecem sem rota
  (financeiro/snapshots, contestação e fluxo de rascunho são missões futuras);
  nenhuma transição fora do grafo é possível pela API.

6. CONCORRÊNCIA (missão item 7):
- Aceite usa UPDATE ... WHERE id = :id AND status='SOLICITADA' AND provider_id
  IS NULL, avaliado pelo banco (rowcount). Dois prestadores simultâneos: exatamente
  um rowcount==1; o outro recebe 409. Não há lógica Python decidindo vencedor.
- Teste test_13 reproduz a corrida com duas sessões que enxergam a mesma linha
  SOLICITADA e executam a MESMA instrução (_stmt_aceite): rowcounts 1 e 0.

7. VALIDAÇÕES DE ENTRADA (Pydantic v2):
- endereco_origem_json: objeto JSON não vazio; data_agendada: datetime COM fuso
  horário (naive => 422); itens: lista >= 1 com marca/dimensao/
  quantidade_declarada > 0 e observacao opcional (<=1000). Constraint de banco
  check_qtd_declarada_positive permanece como segunda barreira.
- codigo_identificador gerado no servidor ("COL-" + hex UUIDv4), UNIQUE preservada.
