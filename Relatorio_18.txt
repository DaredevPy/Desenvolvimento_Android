3. ESTRATÉGIA DE IDEMPOTÊNCIA (doc 09 §4.1 seguido literalmente):
- O app gera UUIDv4 localmente e envia no cabeçalho X-Idempotency-Key
  (opcional até o outbox do Flutter existir; inválido/não-v4 => 422).
- Primeiro processamento: grava a coleta com idempotency_key (UNIQUE já
  definido na migration 001: uq_collections_idempotency),
  idempotency_request_hash = SHA-256 do payload validado
  (model_dump_json) e idempotency_response_json = corpo da resposta;
  retorna HTTP 201.
- Replay da MESMA operação: NÃO re-executa; devolve exatamente a resposta
  armazenada com HTTP 200 (mesmo que o estado atual da coleta tenha
  avançado — provado em teste).
- Mesma chave com payload diferente => 409 definitivo (nada é criado).
- Chave usada por OUTRO usuário => 404 uniforme "Recurso não encontrado."
  (anti-enumeração; a identidade vem SEMPRE do JWT, nunca do cliente).

4. PROTEÇÃO DE CONCORRÊNCIA:
- Dois requests simultâneos com a mesma chave passam pelo mesmo SELECT de
  verificação, mas quem perder a corrida de INSERT recebe IntegrityError
  do UNIQUE no BANCO; o endpoint faz rollback e cai no fallback de replay
  (_replay_idempotente), devolvendo 200 com a resposta do vencedor.
  Determinismo garantido pelo PostgreSQL (constraint + transação), não por
  lógica Python frágil. Fallback só ativa com chave presente (chave None
  re-relança o erro original).
- Teste de corrida usa threads + barreira sobre sqlite em ARQUIVO com
  NullPool (uma conexão por requisição, semântica próxima ao PostgreSQL);
  resultado provado: exatamente 1 coleta persistida.

5. ESCOPO RESPEITADO:
