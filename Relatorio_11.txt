4. MECANISMO RBAC UTILIZADO:
-------------------------------------------------------------------------------
Fábrica de dependência FastAPI em backend/app/rbac.py:

    require_roles("CLIENTE")            # papel exclusivo
    require_roles("CLIENTE", "ADMINISTRADOR")   # papéis múltiplos (doc 04 §2:
        # ex.: ADMIN também executa operações de cliente/prestador)

Encadeamento: require_roles -> get_current_user (identidade, Missão 05) ->
comparação da role CARREGADA DO BANCO (nunca do token nem do corpo da
requisição) -> 403 se não autorizada.
Reutilizável em qualquer router futuro: Depends(require_roles(...)).
Sem hierarquia entre papéis; sem novos papéis; sem matriz complexa.

7. COMPORTAMENTO 401/403:
-------------------------------------------------------------------------------
- Não autenticado (sem token / token inválido / expirado / conta não-ATIVA):
  401 Unauthorized, vindo da autenticação da Missão 05.
- Autenticado sem permissão: 403 Forbidden ("Acesso negado para este
  perfil."), SEM cabeçalho WWW-Authenticate (identidade já validada).
- Autorizado: 200 OK.
Nunca 401 para falta de permissão — verificado por teste explícito.

8. TESTES EXECUTADOS:
-------------------------------------------------------------------------------
python -m unittest discover -s backend/tests -p "test_*.py"
Cenários mapeados: cliente→cliente 200; prestador→prestador 200;
admin→admin 200; cliente→admin 403; prestador→admin 403; cliente→prestador
403; prestador→cliente 403; sem token 401; token inválido 401; role não
autorizada 403; autorização independente de corpo/query (?role=... e JSON
body {"role":...} ignorados na decisão); regressão total das Missões 03-05.

10. PROBLEMAS ENCONTRADOS:
-------------------------------------------------------------------------------
- TestClient.get() do httpx não aceita corpo JSON: corrigido no TESTE usando
  client.request("GET", ...) — que é justamente o cenário sob teste
  (requisição manual com corpo). Nenhuma alteração no código de produção.
- Avaliação do JWT solicitada pela missão: formato atual coerente com
  04_PERFIS_E_PERMISSOES.md §3.1 (sub + role + iat/exp, HS256). A role usada
  na autorização vem do banco via get_current_user, não da claim do token —
  portanto alteração de role no meio da validade do token é refletida
  imediatamente no acesso. NENHUMA correção estrutural foi necessária.
