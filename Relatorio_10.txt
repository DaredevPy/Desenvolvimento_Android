3. DEPENDÊNCIAS ADICIONADAS:
-------------------------------------------------------------------------------
- argon2-cffi==25.1.0 (hashing de senha Argon2id)

Verificação prévia: nenhuma solução equivalente existia no projeto
(passlib/bcrypt/jose não instalados). Escolhas diretas, sem wrappers.

4. ALGORITMO DE HASH UTILIZADO:
-------------------------------------------------------------------------------
Argon2id (primeira recomendação de 08_SEGURANCA.md §3), via PasswordHasher do
argon2-cffi com parâmetros padrão da biblioteca (alinhados a OWASP), sal
único gerado automaticamente por hash. Verificação em tempo constante pela
própria biblioteca. Proibidos e ausentes: MD5, SHA-1, SHA-256 puro.
Nenhuma senha é logada em nenhum ponto do código.

5. ESTRATÉGIA DE AUTENTICAÇÃO UTILIZADA:
-------------------------------------------------------------------------------
Fluxo exatamente como especificado: credenciais -> validação de entrada
(Pydantic) -> busca do usuário por e-mail normalizado (lowercase/strip) ->
verificação do hash -> emissão do token.
Anti-enumeração dupla:
a) Mensagem idêntica "Credenciais inválidas." para usuário inexistente e
   senha incorreta (testada por comparação dos corpos);
b) Equalização de tempo: quando o usuário não existe, um hash dummy é
   verificado antes do 401, evitando oracle de tempo.
Contas com status != ATIVO são rejeitadas em rotas protegidas (doc 04 §3.1).

6. ESTRUTURA DO TOKEN:
-------------------------------------------------------------------------------
JWT HS256 (assinatura via SECRET_KEY de ambiente), payload mínimo conforme
04_PERFIS_E_PERMISSOES.md §3.1:
{ "sub": <UUID do usuário>, "role": <CLIENTE|PRESTADOR|ADMINISTRADOR>,
  "iat": <emitido em>, "exp": <+ACCESS_TOKEN_EXPIRE_MINUTES, padrão 30> }
Não contém: senha, hash, CPF/CNPJ, chave Pix ou qualquer dado financeiro.
A role vai no token por definição documentada, mas NENHUMA autorização a
utiliza nesta missão (ver item 13).

7. ENDPOINTS CRIADOS:
-------------------------------------------------------------------------------
- POST /api/v1/auth/register -> 201 {id,email,role}; 409 duplicado;
  422 entrada inválida. Cadastro público aceita somente CLIENTE/PRESTADOR
  (autoatribuição de ADMINISTRADOR é rejeitada com 422).
- POST /api/v1/auth/login    -> 200 {access_token, token_type:"bearer"};
  401 genérico com cabeçalho WWW-Authenticate.
- GET  /api/v1/auth/me       -> 200 {id,email,role,status}; 401 sem token,
  token inválido, expirado, assinado com chave errada, usuário removido ou
  conta não-ATIVA.
Nota de rota: a missão exemplificava "/auth/me" como conceitual; o prefixo
/api/v1 segue 04_PERFIS_E_PERMISSOES.md §3.1 (rota oficial de login).

10. COMO OS SECRETS FORAM PROTEGIDOS:
-------------------------------------------------------------------------------
- SECRET_KEY lida exclusivamente de variável de ambiente, sob demanda
  (lazy): ausência causa erro explícito ao usar auth — sem default
  inseguro e sem afetar /health.
- .env.example contém apenas placeholder + comando seguro de geração
  (secrets.token_urlsafe(64)).
- Nenhum secret real no código, nos testes ou no Git.
- Alerta do PyJWT sobre chaves HMAC < 32 bytes tratado: segredos de teste
  com comprimento adequado; orientação refletida no .env.example.
