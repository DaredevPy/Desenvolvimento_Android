4. MECANISMOS DE SEGURANCA IMPLEMENTADOS (doc 08 §4):
a) Rate limiting em endpoints publicos sensiveis (login e register).
b) Cabecalhos HTTP de seguranca em TODAS as respostas (inclusive erros).
c) Limite de tamanho de corpo (1 MiB via Content-Length -> 413) e tetos
   de validacao por campo (422).
d) Re-prova de que o hardening nao cria bypass: JWT, RBAC, ownership,
   idempotencia, maquina de estados e regras financeiras re-testados.

5. CONFIGURACAO DE RATE LIMITING:
- Chave de limitacao: IP do cliente (request.client.host), escopo
  separado por endpoint ("login" / "registro"); baldes independentes.
- Janela: deslizante, RATE_LIMIT_JANELA_SEGUNDOS (padrao 60s).
- Limite: RATE_LIMIT_LOGIN_MAX / RATE_LIMIT_REGISTRO_MAX (tentativas por
  janela). Valor <= 0 DESATIVA o mecanismo (padrao do repositorio).
- Resposta quando excedido: 429 com corpo uniforme
  "Muitas requisicoes. Aguarde antes de tentar novamente." e header
  Retry-After (segundos restantes da janela, >= 1).
- Comportamento: tentativas bloqueadas NAO prorrogam a janela; sucesso
  e falha contam igualmente (doc 08 §4.4 cita 5 logins/minuto como
  exemplo — o numero exato fica para a implantacao via .env/Docker).
- Ativacao: DESATIVADO por padrao para nao quebrar desenvolvimento local
  nem os testes existentes (estado em memoria compartilhado pelo processo
  de testes); a implantacao ativa definindo os limites positivos no
  ambiente (.env.example documenta). Sem Redis/infra externa.

6. CABECALHOS ADICIONADOS:
- X-Content-Type-Options: nosniff
- X-Frame-Options: DENY
- Referrer-Policy: no-referrer
- Cache-Control: no-store (respostas carregam dados pessoais/financeiros)
- Content-Security-Policy: default-src 'none'; frame-ancestors 'none'
  (suprimida somente em /docs, /redoc, /openapi.json p/ Swagger UI)
- Strict-Transport-Security: max-age=31536000; includeSubDomains
  SOMENTE com HSTS_ENABLED=true (HTTPS garantido na borda); padrao ausente
  para nao prejudicar desenvolvimento local em HTTP.

7. VALIDACOES ADICIONADAS (rejeicao 413/422 no servidor):
- Corpo > 1.048.576 bytes (Content-Length) => 413 antes das rotas.
- itens declarados <= 200; pneus por lote <= 2000 (testes existentes usam
  ate 500); quantidade_declarada/conferida/coletada <= 1.000.000.
- endereco_origem_json, fotos_divergencia_json e dados_veiculo_json
  limitados a 4000 caracteres serializados (esquema formal segue
  pendente em STATUS §8; aqui apenas se rejeita entrada excessiva).
- Schemas ja estritos (extra="forbid") foram mantidos; nenhum contrato
  existente foi alterado. Headers/path/query ja limitados ou inofensivos
  (X-Idempotency-Key exige UUIDv4; paginacao admin le=100).

10. PROBLEMAS ENCONTRADOS:
- Rate limiting ativo por padrao quebraria a suíte existente (estado em
  memoria compartilhado por todos os TestClient do processo; centenas de
  logins de teste sairiam do mesmo IP "testclient").
- CSP restritiva (default-src 'none') quebraria o Swagger UI local.
- Durante a edicao da suíte, o test_06 chegou a ser perdido num refactor
  do arquivo de teste (detecado pela contagem 19/20 na execucao
  verbosa); restaurado antes da rodada final.

11. CORRECOES:
- Mecanismo de rate limit controlado por variaveis de ambiente, com
  limite <= 0 desligando-o: producao ativa via .env/Docker; testes e dev
  local ficam intocaveis (requisito explicito da missao).
- CSP aplicada somente as rotas de API; documentacao preservada.
- test_06 restaurado; suíte final 20/20.

12. DECISOES TECNICAS:
- Limitador proprio em memoria (stdlib) em vez de dependencia slowapi/
  redis: codigo enxuto, zero infra nova, suficiente para instancia unica
  no Render; limites por ambiente via env (mesmo padrao de
  ACCESS_TOKEN_EXPIRE_MINUTES).
- Chave por IP (e nao por conta): anti brute-force real; mensagem 429
  uniforme para nao introduzir enumeracao. Credenciais invalidas mantem
  401 uniforme com dummy hash Argon2id (tempo constante).
- HSTS por flag: doc exige HSTS apenas com HTTPS garantido; Render serve
  HTTPS na borda e a ativacao fica no ambiente, sem acoplamento.
- Cache-Control: no-store em toda resposta de API (dados sensíveis);
  X-Frame-Options/CSP como defesa em profundidade p/ respostas refletidas.
- Tetos numericos (200 itens / 2000 pneus / 1e6 quantidades): folga ~4x
  sobre o maior caso real citado nos docs (500 pneus) e cortam payloads
  capazes de exaurir CPU/memoria.

13. PENDENCIAS (registradas em STATUS §8):
- Rate limiting por processo: store compartilhado (ex.: Redis) apenas se
  a API escalar horizontal/multi-worker (hoje proibido por falta de
  necessidade explicita).
- Rate limiting por usuario autenticado (100 req/min por token, doc 08
  §4.4): nao implementado nesta missao.
- IP real atras de proxy (Render): exige --proxy-headers/TrustedHost na
  implantacao; sem isso o limitador ve o IP do proxy.
- Corpos sem Content-Length (chunked) escapam do limite de 1 MiB.
- CORS restrito (doc 08 §4.5): origens oficiais do Flutter Web ainda nao
  definidas nos docs — nao configurado para nao inventar contrato.
- Valores exatos de limite de login/registro por ambiente (doc cita
  "5/min" como exemplo) ficam para a implantacao.
